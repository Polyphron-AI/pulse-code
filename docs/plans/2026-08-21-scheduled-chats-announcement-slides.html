Scheduled Chats

Your agents work all day. Now they can start the day without you. A daily check-in that runs on your schedule, on your machine, with your subscription.

Why

Every morning starts the same way

You open Pulse Code and spend the first twenty minutes reconstructing yesterday: what shipped, what stalled, what you promised yourself you'd do first.

That reconstruction is exactly the kind of work an agent is good at — if it could run before you sit down.

What

One chat a day, on a schedule you set

⏰

Pick a time

A daily check-in per project — or one schedule across all your repos. 6:00 AM, your timezone, set once.

💬

Write the prompt

You decide what the check-in does: summarize yesterday, flag open review threads, draft today's plan.

📄

Get a handoff file

The run ends with a concise handoff written into your project — the briefing for your day, and the agent's memory for tomorrow.

How it works

A loop that compounds

1

Reads yesterday

The scheduled run opens with yesterday's handoff file, so it never starts cold.

2

Does the check-in

Your prompt, your provider, your project — a normal agent turn, just unattended.

3

Writes today

The summary lands in handoff/2026-08-21.md. Plain markdown, in your repo, yours.

4

You wake up briefed

Read it on your phone before you're at the desk. Tomorrow's run reads it again.

No hidden memory store. The agent learns your patterns the same way you would — by reading its own notes.

The deliverable

The handoff file

handoff/2026-08-21.md # Daily handoff — Thu Aug 21
## Yesterday
- Shipped OAuth host-protection gate (3 commits)
- Desktop separation PR still waiting on review
## Today
- Windows ACL gap blocks release — start here
- Two flaky mobile tests, likely the same root cause
## Watch
- npm publish token expires Friday

Small, honest, and in your project — grep it, diff it, commit it.

Trust

Unattended, never unaccountable

  • Every run is a normal thread. Full transcript, full diff, full checkpoint — review the morning run exactly like any other chat. scheduled badge included.
  • It ran once, or it tells you why not. Exactly-once per day, even across restarts. A failed run says so — no lying green checkmarks.
  • Missed mornings catch up. Laptop was asleep at 6 AM? The run fires when your server is back, and never doubles up.
  • Pause anytime. One toggle. Your history stays.

What it is — and isn't

A check-in, not a workflow engine

In the box

  • One daily run per schedule — time + timezone
  • Your prompt, or a project workflow script
  • Handoff file written on completion
  • Pause, resume, delete — history stays
  • Failure surfaced honestly in the UI

Deliberately out

  • Cron expressions and trigger graphs
  • Chained or event-triggered automations
  • Unreviewed codebase mutation overnight
  • Notification fan-out (later, and outbound-only)
  • A generic autonomous workflow engine

Same Pulse Code promise as always: open source, your machine, your subscription — now with a standing appointment.

Under the hood

The cron worker is dumb.
Orchestration holds the truth.

Schedules and every occurrence are event-sourced domain state — the timer never owns anything. A sweep asks the read model "what's due?" and dispatches ordinary commands through the same decider as every user action.

ScheduleReactor (30s sweep) → "due since lastOccurrenceKey?" → dispatch thread.turn.start + bootstrap.createThread
decider (pure) → schedule.occurrence.started → normal turn → settled → handoff write → schedule.occurrence.completed
Under the hood

Exactly-once lives in the decider

  • Deterministic command id — scheduled:<scheduleId>:<2026-08-21> flows through the existing command-receipt idempotency. A restart, double tick, or catch-up sweep cannot double-fire a day.
  • The decider rejects replays — an occurrence whose key matches lastOccurrenceKey never becomes an event. The timer is not trusted; the pure function is.
  • Catch-up is the design, not the edge case — the sweep computes everything due since the last occurrence, so sleep, restarts, and background-service updates resolve on wake.
  • Effect Clock throughout — TestClock drives the tests; no sleeps, no polling, no receipts (the live receipt bus is a no-op — completion uses the settled-turn path).
Under the hood

Typed end to end

  • Contracts first — ScheduleId brand, project.schedule.create/update/pause/resume/delete commands, schedule.occurrence.* events in packages/contracts. Server, web, desktop, and mobile all follow the schema.
  • Threads gain an origin — origin: user | schedule:<id>, so every client and every future feature can distinguish scheduled work without a side channel.
  • Prompt source is future-proofed — v1 accepts raw prompt text, but the contract carries workflowScriptRef from day one, pointing at the existing project workflow scripts.
  • One new reactor — registered alongside Checkpoint and ThreadDeletion reactors, shaped like ProviderSessionReaper but unparked: a parked scheduler defeats the point.
Looking ahead

Future orchestration sees this for free

Because occurrences land on the same event log as everything else, later orchestration plans need zero changes to the scheduler to build on it:

  • A future workflow engine subscribes to schedule.occurrence.* like any other domain events.
  • The read model already answers "what ran, when, did it finish" for any client or integration.
  • Thread origin attribution extends the integrations operate-scope model if external actors ever trigger runs.
  • A "morning run finished" push later hangs off the awareness relay — outbound-only, default silent, per the collaboration-notifications constraints.
Constraints

What we say out loud

  • Runs need a running server. The Linux background service is the natural host; desktop-only users get catch-up-on-launch — stated plainly in user docs, not buried.
  • No new credential surface. Unattended runs use the provider credentials the server already holds; the Windows secret-ACL gate and externally-managed-credential gap apply unchanged.
  • No retries. A failed run surfaces the failure; tomorrow reads the last successful handoff. Simple and honest beats clever and opaque.
  • Two scopes. A project schedule runs one daily check-in; an environment schedule fans out one thread per selected repo — e.g. a nightly sweep deciding commit-and-push vs open-a-PR, every run individually reviewable.
Process: not on the roadmap yet — needs a PRD change request, a T1 "Connected work loop" slot tradeoff in roadmap.yaml, and this design doc blessed before build.
Shipping it

Build order

  1. Contracts + decider + projector — schedules, occurrences, thread origin, with focused decider tests.
  2. ScheduleReactor — sweep, catch-up, idempotent dispatch; TestClock-driven tests.
  3. Handoff writer — settled-turn subscription, atomic file write, occurrence completion.
  4. Web + desktop UI — settings editor, thread-list section, command palette entry.
  5. Mobile — Scheduled section and handoff reading view.
  6. Docs — user page in shipped-product voice, glossary entries for schedule, occurrence, handoff file.
