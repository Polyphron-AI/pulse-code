Security boundary · approved with constraints

Credentials stay behind the server boundary.

The current secret store is acceptable for a single-owner, trusted Pulse Code Server. Shared or untrusted hosts remain release-blocked until isolation, redirect replay, backup, diagnostics, and provider-revocation controls are evidenced.

Approved scopeSingle trusted OS account with a private data directory
Blocked scopeShared or untrusted host OAuth release

Security decision

Suitable, but accurately described

OAuth release-blocked
Accepted

ServerSecretStore

Filesystem-protected storage is suitable when one trusted OS account owns the server data directory. Pulse Connect already rotates refreshed credentials through the same boundary.

Do not claim

Encryption or hardware backing

The current store is not encrypted at rest. Do not describe it as platform-keychain, hardware-backed, or portable Windows ACL protection.

Ownership rule: the owning server is the only provider API client. Web, desktop, mobile, relay, and agent surfaces receive credential-free connection snapshots only.

Evidence by control

What is protected today

Each control has a precise release consequence; passing one does not silently close the others.

Control Observed behavior Release consequence
At rest Raw bytes live at userdata/secrets/<name>.bin; directory 0700, files 0600. Accept for an isolated owner account. Not encryption; POSIX modes are not portable Windows ACL evidence.
Writes UUID-named temporary file, secure rename over active file, exclusive wx create, sync, and chmod. Tested rename failure cannot report success. Platform rename semantics still require compatibility testing.
Reads Missing files become Option.none; other failures become typed errors. Bytes stay inside the server process. Snapshots expose configured state and non-secret hints only.
Rotation Pulse Connect refreshes early and persists the refreshed pair through set under a semaphore. Adapters must persist a rotated refresh token before returning it as durable.
Deletion remove is idempotent for a missing file and surfaces other failures. Disconnect revokes upstream when supported, then removes local secret; local failure is not success.
Logging/errors Spans name the operation, not the value. Expected errors contain resource label and platform cause. Provider bodies and authorization headers never enter public errors.
Backups SQLite-only rollback snapshots exclude secrets; a whole userdata copy includes them. Whole-directory backups are credential-bearing and need equally restrictive storage/deletion.
Diagnostics No current diagnostic export copies the secret directory. Future exporters must explicitly exclude secrets, OAuth fields, and provider response bodies.

OAuth redirect-state contract

State is a one-time nonce, not sign-in

Required for every provider
  1. Generate state and PKCE verifier from a cryptographically secure source; state has at least 128 bits of entropy and never encodes a credential.
  2. Bind the attempt to provider, environment, initiating session/user, exact redirect URI, and PKCE verifier.
  3. Expire it after a short fixed interval; the existing loopback flow uses ten minutes and a provider may use less, never more.
  4. Consume state atomically before token exchange and mark it consumed even when exchange fails.
  5. Reject missing, mismatched, expired, or replayed state with the same bounded public failure.
  6. Keep transient state in server memory; if restart survival is required, persist only a digest/binding metadata and keep the verifier in the secret boundary.
  7. Never log or export state, authorization codes, PKCE verifiers, tokens, headers, or token endpoint bodies.

Session rule: a callback may complete the initiating session’s attempt, but it must not create a new ambient session.

Named release blockers

Four gates before provider OAuth

These blockers do not prevent additive lifecycle contracts or credential-free connection persistence.

INT-SEC-01

Host isolation policy

Prove a dedicated private OS account and protected directory, or supply a reviewed encrypted backend. Windows packaging must verify effective ACLs.

INT-SEC-02

Redirect replay suite

Cover valid consume, environment/session mismatch, expiry, duplicate callback, and replay after failed exchange. No stateless fallback.

INT-SEC-03

Backup and diagnostic disclosure

Document whole-directory backup risk and attach proof that userdata/secrets and prohibited OAuth fields are excluded from diagnostics.

INT-SEC-04

Provider disconnect semantics

Declare and test upstream revocation ordering. If unsupported, the UI must say provider-side grants may need manual revocation.

Release checklist

Current posture at a glance

4 open
  • Secret values stay server-owned and outside integration snapshots.
  • Expected store errors do not retain or serialize supplied secret bytes.
  • Rotation and deletion primitives return typed failures.
  • Database-only update snapshots exclude the secret directory.
  • INT-SEC-01 deployment/Windows ACL evidence is attached for target release platforms.
  • INT-SEC-02 redirect-state replay tests pass in the integration service.
  • INT-SEC-03 backup wording and diagnostic exclusion evidence are attached.
  • INT-SEC-04 provider-specific revocation behavior is implemented and documented.

Allowed now: T3 may build server-owned, credential-free connection and mapping records while these OAuth release gates remain open.
