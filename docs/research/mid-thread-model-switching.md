# Switching models and providers mid-thread: market research and Pulse Code recommendation

Research date: 2026-09-04  
Audience: Pulse Code product and engineering maintainers  
Decision: how a user moves a running thread from one provider or model to another, especially when a subscription's usage runs out

## Executive summary

Every serious coding agent now lets a user change the model inside a conversation. The market splits on **what happens to the context** when the new model belongs to a different provider, because a provider's transcript is not portable: reasoning traces, tool-call ids, and cache state only make sense to the model that produced them.

Three approaches exist:

1. **In-session switch.** Same provider, same session, next turn uses the new model. Claude Code, Codex CLI, Aider, Copilot Chat, Windsurf. Cheap, exact, and already how Pulse Code works today for same-provider changes.
2. **History replay.** The app owns the API calls and re-sends the whole transcript to the new provider, dropping or lowering provider-private parts. OpenCode, OpenRouter-style chat apps. Only possible when the app speaks the model API directly. Pulse Code wraps provider CLIs, so this is not available to us.
3. **Handoff to a new thread.** A second model extracts what matters from the old thread, the user reviews an editable draft, and a new thread starts fresh with it. Amp made this its only long-context tool and retired compaction. Zed, Cursor (limited), and Cline's `new_task` follow the same shape.

**Recommendation:** Pulse Code should ship approach 3 as the cross-provider switch, triggered from the model picker inside a started thread, and keep approach 1 for same-provider model changes. The new thread carries a structured handoff built from the persisted transcript, is linked back to the source, and the source settles. The usage-limit case is the same flow with a smarter entry point: when a provider reports its plan window exhausted or a turn fails on a limit error, the composer offers "Continue with another provider" instead of a dead retry button.

Two lessons from the field shaped the details below: Amp's finding that extraction beats stacked summaries, and Zed's bug where the summary was generated by the very provider the user had run out of credit with. The handoff text must be generated by the **destination** provider, never the exhausted one.

### Where the market agrees

- The picker lives in the composer and applies to the next turn. No settings trip.
- Same-provider switches are exact and in-session. Cross-provider switches are a new session, whether the app admits it (Amp, Zed, Cursor) or hides it behind replay (OpenCode).
- Reasoning traces and provider-native tool metadata never cross providers. Tool results survive as plain facts.
- The handoff is a draft the user can edit before sending. Every product that skipped review (Copilot fallback, Cursor auto-summary) drew complaints.
- Stacking summaries degrades work. Amp dropped compaction for this reason; Codex keeps recent verbatim messages alongside the summary.

## Constraints specific to Pulse Code

Pulse Code does not call model APIs. It drives provider CLIs (Claude Code, Codex app-server, Cursor, Grok via ACP, OpenCode) and stores an event-sourced transcript of what crossed orchestration. That fixes several things:

- **Replay is impossible across providers.** A Claude Code session id means nothing to Codex. The only carrier is text in the first prompt of a new session. This is why the design is a handoff, not a fork.
- **Same-provider switches already work.** Every adapter reports `sessionModelSwitch: "in-session"` and the reactor either passes the new model on the next turn or restarts the session with the same resume cursor. Nothing to build there.
- **Cross-provider switches are rejected today.** The reactor refuses a turn whose instance has a different driver kind or continuation key, and the web composer locks the picker to the active session's instance. The feature is largely lifting that lock into a guided flow.
- **We already know when usage runs out.** Codex and Claude both stream plan-usage windows that the server merges into `ServerProviderPlanUsage` and the Usage page renders. Cursor, Grok and OpenCode do not, so for them the only signal is a failed turn.
- **Provider-private context is lost by definition.** Sub-agent work, tool payloads never surfaced, and reasoning never reach the transcript. The UI must say "carries the visible conversation", not "carries everything".

## Decision

Build cross-provider model switching as a **thread handoff**: settle the source, create a linked destination thread on the chosen provider, and start it with an editable, structured digest of the persisted conversation. Reuse the settled-thread handoff design from 2026-08-28 for the server plumbing (preview RPC, start RPC, `sourceThreadId`, capability flag) and add the model picker and usage-limit entry points on top. Keep same-provider changes in-session as they are.
