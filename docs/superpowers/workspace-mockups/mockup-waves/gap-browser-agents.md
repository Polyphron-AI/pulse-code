## 3. Code function

### Existing shared data and action paths

**Verified source.** `WorkspaceItemRef` already has `url`, `thread`, `project`, `task`, `mail`, `file` and `provider-resource`; it has no dedicated `agent` or `browser-page` variant. URLs accept http/https, up to 2048 characters. Canonicalization removes fragments and `utm_` parameters while preserving surviving query bytes. Threads use `thread:<encoded id>`, pages `url:<encoded canonical URL>`. Reuse these identities. Evidence: `packages/contracts/src/pulseLinks.ts:14`, `:41`, `:66`, `:81`, `:124`.

**Verified source.** Link endpoints carry an optional title. `pulse.links.link` writes two endpoints with optional viewing origin and user/action source; list, listMany, projectHub, unlink and subscribeChanges already exist. The service rejects self-links, confirms through the repository and announces changes. Agent context uses confirmed links attached directly to the calling thread or its project. Evidence: `packages/contracts/src/pulseLinks.ts:152`, `:158`, `:251`; `apps/server/src/workspace/WorkspaceLinks.ts:187`, `:201`, `:229`, `:244`.

**Verified source.** `workspaceLinks.list`, `listMany` and `projectHub` refresh when the environment's change stream ticks; mutations serialize per environment. The WS layer delegates to the shared service. Evidence: `packages/client-runtime/src/state/workspaceLinks.ts:19`, `:54`, `:68`, `:75`; `apps/server/src/ws.ts:1415`.

**Proposed default.** Keep a shell-selected resource project distinct from the selected main-area item. Browser and Project agents use that resource project; Links continues to show the selected item's confirmed links. A visible target label makes `Link this page` unambiguous. Opening or navigating a page never links it automatically. Assigning a thread to Project agents is an explicit thread-to-project link, not an inference from its presence in the project thread list. This preserves the requirement that links are user-confirmed while matching the mockup's project resource header.

### Browser ownership, remote clients and phone degradation

**Verified source.** Desktop capability is detected from `window.desktopBridge?.preview`, not from the server's operating system. PreviewPanel explicitly says preview is desktop-only without that bridge. A desktop connected to a remote environment still passes the selected environment/thread to the preview RPC. Evidence: `apps/web/src/previewStateStore.ts:462`; `apps/web/src/components/preview/PreviewPanel.tsx:31`; `apps/web/src/components/preview/openPreviewSession.ts:44`. The existing test checks `{environmentId:"remote",threadId:"t"}` reaches the open helper, but this is a mocked test, not remote browser verification: `apps/web/src/components/workspace/WorkspaceToolsPanel.test.tsx:153`.

**Verified source.** Electron's Browser session uses persistent or ephemeral partitions, and preview preferences keep sandbox enabled and Node integration disabled. Reuse these boundaries. Evidence: `apps/desktop/src/preview/BrowserSession.ts:14`, `:182`, `:193`; `apps/desktop/src/preview/WebviewPreferences.ts:15`, `:42`. A resource tab must not bypass preview attachment/profile rules.

**Platform constraint supplied in the task.** Web cannot reliably embed arbitrary sites because sites can deny framing through X-Frame-Options or CSP frame-ancestors. A parent web app also cannot read an unrelated external tab's navigation, DOM or cookies. No network/header checks were performed here. An iframe, header-stripping proxy or server screenshot stream is not a default substitute for Electron preview.
